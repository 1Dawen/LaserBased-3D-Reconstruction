# Technical notes and limitations

## Source material

The supplied archive contained exactly three files: one original single-cell notebook (`Code.ipynb`), the two-page final exam report, and `F11215109.xyz`. Neither the `colour/` nor `laser/` source-image directories were included. The archived XYZ file has **300,142 colored points**; this is an original archived output, not a reconstruction generated by this repository's tests.

The report documents a manual four-point camera-to-laser-plane calibration, background subtraction of laser-off/on pairs, one Gaussian-weighted column per image row, homography transformation to the laser plane in millimeters, turntable Y-axis rotation at **one degree per frame**, and sampling each point's RGB from its laser-off image. The original notebook implements this procedure. The refactored pipeline follows those steps while adding structured input validation, CLI options, reusable functions, and tests.

## Calibration and geometry

The original notebook's source points and destination coordinates appear unchanged in `configs/original_calibration.json`. Those points belong to its specific, now-unavailable calibration photographs and should **not** be used for arbitrary new images. A new scan needs a matching calibration and appropriately positioned turntable rotation axis.

Given a detected pixel `(col, row)`, OpenCV applies the 3x3 homography to obtain `(X_plane_mm, Y_plane_mm)`. For a rotation angle `theta`:

- `X_world = X_plane_mm * cos(theta)`
- `Y_world = Y_plane_mm`
- `Z_world = X_plane_mm * sin(theta)`

This assumes the laser plane intersects the turntable's Y-axis as in the original assignment. It is **not a general calibrated camera-ray/laser-plane triangulation system**; calibration and alignment errors can distort the result. The original report states that the orientation of the resulting cloud needed correction in CloudCompare, not within the notebook. No geometric accuracy measurements or error bars were supplied.

## Detection behavior

The default detector reproduces the notebook's `cv2.absdiff` -> grayscale -> threshold 10 -> median filter 5 process. For each nonempty image row it computes the Gaussian-weighted average of illuminated columns (sigma = 3), rounding to one pixel. This can be affected by reflections, lighting changes, occlusion and multiple laser stripes in a single row. The optional `--channel green` mode detects *increases* in green brightness; it is an experimental alternative, **not** a method used in the original report. Colors are sampled at the selected pixel in the background BGR frame, then written in RGB order.

## Provenance of images

- `docs/original_point_cloud_preview.png` plots a reproducible random subset of the **archived 300,142-point scan**. It gamma-brightens the sampled RGB values to make the dark scan easier to see, without changing geometry or the underlying XYZ file.
- `docs/synthetic_point_cloud_preview.png` uses **fictional paired images** from a deterministic code-generated sequence. It verifies software behavior; it is not a scan of a real object and does not evaluate reconstruction quality.

## Reproducibility status

Tests validate calibration, laser row extraction, rotation, RGB channel order, file handling, and synthetic image-pair processing. They do not verify the historical physical experiment or establish depth accuracy, coverage, or noise robustness on real photos. The original image sequences and alignment parameters remain unavailable. Accordingly the archived original cloud cannot be independently reproduced from repository assets alone.
